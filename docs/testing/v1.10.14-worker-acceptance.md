# v1.10.14 Worker acceptance checklist

This checklist is the manual Android gate for issue #33 / regression #29. Automated Go/JVM tests cover deterministic transport semantics; these checks must be run on a real Telegram client before v1.10.14 is released.

## Build under test

Record before testing:

- branch / commit SHA;
- app version and versionCode;
- Android device and Android version;
- Worker hostname used;
- whether `EXPERIMENTAL_FORCE_MEDIA_DC4` is enabled.

Do not paste MTProto secrets into the report.

## Build, install and collect logs

Run from the updated PR #39 checkout in Windows PowerShell:

```powershell
.\scripts\test-worker-device.ps1
```

The script builds Debug, installs it without removing app data, opens the app, and records Logcat until Enter is pressed. Files go to `artifacts/worker-tests/`; metadata includes commit and APK SHA-256. Use `-DeviceSerial SERIAL` when multiple devices are attached. `-SkipBuild` intentionally reuses the existing APK and is only for repeating a test of that build.

Before testing, deploy the matching [Worker source](../../scripts/cloudflare-worker/worker.js), set `WORKER_DIAGNOSTICS=1`, and open Cloudflare live logs. Enable Android runtime logging, restart the proxy, and confirm `worker_revision=worker-stream-v2`.

Begin with `PRESERVE_ORIGINAL_DST`, then test the destination override separately. Upload **and** download a file larger than 20 MiB. Record both DC2 `media=false` bulk sessions and `media=true` sessions; both matter. Correlate Worker `sid` with Android `session_id`. Complete transfers plus downstream are required; write counters or HTTP 101 alone do not pass this gate.

The automated TLS test uses a real local TCP/TLS connection. Worker JavaScript tests execute the deployable handler with simulated Cloudflare sockets and slow/failing sinks. Neither test substitutes for this real-device gate.

## September 11: TCP delivery loss and TLS record experiment

The full Android run `worker-runtime-20260910-225423.txt` on `aff1162c` contains
16 stalled sessions. Across the captured samples of each session, `bytes_acked`
does not advance (8,322–16,650 bytes, most often 13,088); retransmissions increase,
`cwnd=1`, and `snd_wnd` stays nonzero at 122,880–147,456 bytes. The 458,752-byte
bridge plateau measures data accepted locally, not delivery to Cloudflare.

The original Cloudflare JSON and Android log have eight matching closed sessions
with `received_bytes=64`, `tcp_written_bytes=64`, `downstream_bytes=0`, and
`pending_bytes=0`. Android had accepted between 25,335 and 458,752 payload bytes in
those sessions. Thus their payload never reached the Worker message handler.
Other sessions receive Telegram responses through the same Worker. The originally
quoted `a0beb70eddbb6553` is absent from the Cloudflare export; do not substitute
another session's counters for it.

This localizes the observed delivery failure to the Android-to-Cloudflare path.
It does not identify the device, network, middlebox or edge component responsible.
A nonzero peer receive window and growing retransmissions do not support the old
theory that Telegram TCP writes are filling the Worker queue.

Two separate cancellation defects reproduce locally and are corrected: a failed
write could be hidden by the parallel reader's `closed connection` error, and
`tls.Conn.Close()` could wait another five seconds trying to send `close_notify`
after the write deadline had been cleared. Both have regression tests. New
`MTProto Worker transport closed` lines capture TCP counters before cancellation,
including sessions that end before a write fills the local send buffer.

The next isolated network experiment sets
[`DynamicRecordSizingDisabled`](https://pkg.go.dev/crypto/tls@go1.25.0#Config) for
the Flowseal Worker TLS connection. The Go baseline uses adaptive TLS record sizes;
[Flowseal's Python transport](https://github.com/Flowseal/tg-ws-proxy/blob/main/proxy/raw_websocket.py)
uses OpenSSL. The local TLS test verifies that the new profile sends a 64-KiB
WebSocket payload in four full TLS records plus the frame-header remainder, and
that both adaptive and fixed profiles preserve payload bytes in both directions.
This changes TLS records, not the already-tested 16-KiB transport-write splitting
or RFC6455 message fragmentation. It is an experiment, not a verified network fix.

For the next run:

1. Use the existing `worker-stream-v2` deployment; this change requires an updated APK.
2. Run `scripts/test-worker-device.ps1` and confirm both `worker_revision=worker-stream-v2`
   and `tls_record_sizing=fixed` in `transport ready`.
3. Start with Worker only, preconnect off, `PRESERVE_ORIGINAL_DST`. First check that
   Telegram leaves its connecting state and sends/receives a text message; only
   then try a transfer larger than 20 MiB.
4. Keep the whole Android log. Compare `transport closed` and `TCP stalled`
   counters with the baseline above, and correlate a failing `session_id` with
   Cloudflare `sid` if needed.
5. If ACKs remain flat and the Worker still receives only the 64-byte init, reject
   the record-sizing hypothesis. Compare the same endpoint/network with desktop
   Flowseal and the same Android APK on another network before changing TLS again.

Passing unit tests or a different error message does not pass the connection or
media acceptance gate. Do not release this experiment as a demonstrated fix.

## Bridge diagnostics

For every unexpectedly short Worker session, inspect:

```text
MTProto bridge closed ...
first_terminator=...
close_reason=...
up_bytes=...
down_bytes=...
up_chunks=...
down_chunks=...
duration_ms=...
error=...
```

Interpretation:

- `first_terminator=client_to_upstream close_reason=eof`: the local Telegram side closed first;
- `first_terminator=upstream_to_client close_reason=eof`: Worker / Telegram upstream closed first;
- `write_error`: forwarding failed while writing to the opposite side;
- `read_error`: forwarding failed while reading;
- `cancelled`: secondary direction was closed because the other direction already ended.

A successful HTTP 101 / `MTProto route connected` is **not** sufficient acceptance. The session must transfer payload in both directions and media upload/download must complete.
